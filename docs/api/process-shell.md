# Process and Shell API

状态：`contract-only`；`Run` 与 `ProcessClose/ProcessExist/ProcessGetName/ProcessGetParent/ProcessGetPath` 已实现；`RunWait`/`ProcessWait`/`ProcessWaitClose`/`RunAs`/`Shutdown`/`ProcessSetPriority` 本轮已实现到 service + executor + JS 模块，并已在 `contracts/registry/actions.json` 与 `Bootstrap` 完成注册（见文末交付状态）。全部 contract 见 `tests/native/process_tests.cpp`。

命令解析（`Run` → `process.launch` → `ProcessService::launch`）：裸命令（不含盘符与路径分隔符 `\`、`/`）先经 `SearchPathW` 按 Win32 搜索顺序（应用目录、当前目录、系统目录、Windows 目录、`PATH`）解析为绝对路径，再以该绝对路径作 `lpApplicationName` 交给 `CreateProcessW`；无扩展名的裸名先按 `.exe` 查找，未命中再按原名查找一次，已带扩展名的裸名只按原名查找。带路径的命令不参与搜索、原样传入，全路径行为与命令行拼接（`"command" + args`）、`workingDir`、异步语义均不变。搜索不到且 `CreateProcessW` 也失败时返回 `execution_failed`，消息写明 PATH 搜索失败并附 Win32 错误码。历史缺陷：裸命令曾直接作为 `lpApplicationName` 传入，而 Win32 只按当前目录补全、不做路径搜索，导致 `notepad.exe` 之类命令必须靠切换当前目录才能启动；该绕行已由本次解析修复取代。验证：`tests/native/process_tests.cpp`（裸名与全路径两条输入都走 `ProcessService::launch`）、`tests/native/golden_exec_tests.cpp`（golden 裸 `notepad.exe` 从测试自身 cwd 启动，不再切目录）。

源码证据：`functions.h` 的 `Run`、`RunWait`、`RunAs`、`Process*`、`Shutdown`；`source/lib/process.cpp`、`source/application.cpp`；Runtime 侧 `engine/win32/src/process.cpp`（`ProcessService`：`launch/launch_waitable/wait_ref/cancel_wait/open_waitable_pid/open_waitable_count/stop/set_priority/run_as/shutdown_system`）、`engine/win32/src/process_executor.cpp`（`process.launch/process.terminate/process.set.priority/process.runas/process.shutdown` 五路分派）、`engine/win32/js/src/process_module.cpp`（10 个模块导出）。

进程使用稳定 `ProcessId` 和快照；启动返回受 Runtime 所有的 `ProcessRef`（不暴露到 JS）。

**等待与可等待句柄。** `launch_waitable` 把 `CreateProcessW` 返回的 `hProcess`（`SYNCHRONIZE` 权限）登记进 service 私有的引用表，签发单调递增、从 1 开始的 `ref_id`；`wait_ref(ref_id, deadline_unix_ms, exit_code, timed_out)` 每次最多阻塞一个 25ms 分片：`WAIT_OBJECT_0` 时消费引用并返回真实退出码，超时保留引用并置 `timed_out`，引用为 0、未签发、已消费分别以 `invalid contract` 拒绝。`cancel_wait` 释放引用，重复释放是 contract 错误。三种等待的分工：`ProcessWait`（`wait`）只按快照轮询存在性——pid 已消失就无法再开句柄；`ProcessWaitClose`（`waitClose`）先用 `open_waitable_pid` 开一个 `SYNCHRONIZE` 句柄、开不到退回快照轮询，已消失即命中；`RunWait`（`runWait`）在 worker 线程上 `launch_waitable` 后等待该句柄。三者都以 25ms 分片推进，不阻塞 JS Thread；`open_waitable_count()` 与 `stop()`（返回释放数、幂等）供泄漏诊断与宿主停止链使用。

**JS 导出与取消。** 导出 10 个：既有 `list/info/launch/terminate`，新增 `wait(pid, options?)`、`waitClose(pid, options?)`、`runWait(request, options?)`、`setPriority(pid, priority, options?)`、`runAs(request, options?)`、`shutdown(payload, options?)`。等待三兄弟用 `begin_async` 但**不绑定 cancellationId**：每步自检 `host->is_cancelled(0)` 主动 `cancel_wait` 后 reject——因为 `apply_completion` 的 CancelById 路径会先拆掉 25ms timer，循环再也醒不来、引用泄漏。`setPriority/runAs/shutdown` 走 `run_action` 并传入 `options.cancellation_id`。超时（默认 5000ms，作用于全部 entry 包括 `runWait` 的等待段）reject `timeout` 并释放引用，子进程继续运行但不再被等待；任务调度失败（teardown）由宿主 reject，残余引用交给 `ProcessService::stop()`/析构清扫。

**ProcessSetPriority。** 动作类型 `process.set.priority`，capability `process.manage`；payload `{pid, priority}`，`pid` 与 `action.target.id` 必须一致且为正，`priority` 六拼写 `idle/belowNormal/normal/aboveNormal/high/realtime` 由 `is_valid_priority` 单一口径校验（service 与 executor 共用）。成功 detail 为 `priority updated`；`realtime` 提权失败返回 `realtime priority requires elevation (win32 error N)`，不隐式提权。不一致、未知拼写、缺字段、非正 pid 一律 `invalid contract`，在打开进程之前拒绝。

**RunAs。** 动作类型 `process.runas`，capability `process.runas`，`action.target.id` 必须是 `new`；payload `{user, password, executable, args, workingDir, options}`，密码是必填字符串，空用户、空可执行文件、可执行文件含 `"`、缺密码都在 `CreateProcessWithLogonW` 之前以 `invalid contract` 拒绝。凭据只进 payload：Trace 记录不包含 payload，错误消息不回显密码。成功 detail 为 `process created`。

**Shutdown。** 动作类型 `process.shutdown`，capability `process.shutdown`；payload `{mode, force, timeoutSec}`，`mode` 为 `logoff/shutdown/reboot/poweroff/hibernate`，`force` 必须是布尔，`timeoutSec` 0..600 整数且非零时只允许 `shutdown/reboot`（与 AHK `Shutdown()` 的位映射语义对应），`force` 与 `hibernate` 组合拒绝。校验顺序：mode 枚举 → 超时范围 → 超时与 mode 匹配 → force/hibernate，全部通过后才可能启用 `SeShutdownPrivilege` 或调用 `InitiateSystemShutdownExW`/`SetSuspendState`。成功 detail 为 `shutdown requested`。

**刻意未测与测试政策。** shutdown/run_as 只测拒绝路径：两者成功会结束会话或需要真实凭据，因此 contract 测试用“至少一个非法字段”保证任何路径都碰不到 OS 调用（该不变量在测试内显式注释）。真实副作用只覆盖本文件自启子进程的优先级类读回（`GetPriorityClass`）、退出码与存活消失，且清理都在测试内完成。

**交付状态（集成方已落地）。** `contracts/registry/actions.json` 已注册 `process.set.priority`/`process.runas`/`process.shutdown` 三个 type，`capabilities` 中 `process.manage`/`process.runas`/`process.shutdown` 均为 `implemented`，`production_capabilities()` 现为 20 项；`register_executors` 三个 type 已登记，`ProcessService::stop()` 已接入 `Bootstrap::stop()`（在 automation/window/input 之前执行，先释放等待引用与残余句柄）。`process.set.priority`/`process.runas` 的小写分段是刻意为之——旧的驼峰写法对扫描正则不可见，会形成永久漂移。**仍存缺口**：JS 侧 wait 循环（`process_wait_step` 等）尚无测试覆盖——service 层 `wait_ref`/`cancel_wait`/`open_waitable_*` 由 `tests/native/process_tests.cpp` 覆盖，JS 侧只有 `breadth_slice` 对既有导出的冒烟。
